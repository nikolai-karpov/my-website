## Кейс A. Платформа управления перевозчиками

### Один абзац (хук)

Сквозная веб-платформа для логистики промышленного холдинга, объединяющая управление двором (Yard Management), групповую обработку заказов на один адрес, агрегатор тарифов транспортных компаний, цифровую среду работы с перевозчиками (тендеры, рейтинги, смарт-контракты, ЭДО, штрафы) и сигнальную систему предотвращения перезатарки складов. Главная ценность — уход от Excel-бронирования и ручного цикла претензионной работы при сохранении совместимости с действующей 1С УПП и будущей 1С:ERP, чтобы переход на ERP не обнулял инвестиции. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L9-L22]

### Контекст и задача

Логистика заказчика опиралась на общий Excel-файл бронирования окон (однопользовательский режим, перезаписи последним сохранившим, не учитывались коэффициенты сложности заказа К1—К4, не было синхронизации с WMS и 1С), на ручной ввод множественных заказов на один адрес (пример из 1С: 6 заказов на одну точку выгрузки) и ручной обзвон/расчёт тарифов по 5+ транспортным компаниям. Дополнительно фиксировалась перезатарка складов >95% в конце месяца и полностью ручной цикл оформления штрафов перевозчикам. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L23-L91]

AS-IS-анализ зафиксировал пять системных болей: фрагментация и дублирование данных по бронированию; отсутствие единой картины очереди и статусов отгрузки; неэффективное планирование слотов; зависимость от ручной координации; слабая сквозная аналитика простоев и штрафов. [источник: 04_ВСТРЕЧИ_И_ПЕРЕГОВОРЫ/Протоколы/Протокол_складская_логистика.md:L45-L51]

### Роль автора в проекте

Инициатор и идеолог решения. Провёл диагностическое интервью с директором по логистике, зафиксировал AS-IS и узкие места, оформил протокол с поручениями, подготовил «Описание решения. Версия 2.0» (структура контуров A–E, архитектурные принципы, карта интеграций, дорожная карта из 8 этапов, риски, ближайшие шаги). Определил «внутреннего агента» от логистики для пилота (аналитик по запасам + начальник склада). [источник: 04_ВСТРЕЧИ_И_ПЕРЕГОВОРЫ/Протоколы/Протокол_складская_логистика.md:L57-L65] [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L7,L335-L346]

Кроме описания, силами автора подготовлен HTML-прототип интерфейса бронирования окон (страница `yard_booking.html` с таймлайном слотов, коэффициентами К1–К4, индикаторами заполненности). [источник: 02_ПРОЕКТЫ/Складская_логистика/yard_booking.html]

### Архитектура (высокий уровень)

- **Назначение**: единая веб-платформа автоматизации складской и транспортной логистики, спроектированная как «обёртка» над 1С УПП и будущей 1С:ERP. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L11-L13,L93-L110]
- **Основные модули (контуры)**:
  - Контур A — **Yard Management**: веб-бронирование окон, авторасчёт длительности по коэффициентам К1–К4, лимиты на окно (число машин, суточная нагрузка), очередь ТС, push/email-уведомления, мобильная версия для начальника склада, история бронирований для калибровки нормативов. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L114-L139]
  - Контур B — **Групповая обработка заказов на один адрес**: автогруппировка по «место погрузки + место выгрузки + дата», мастер-заявка, объединение в рейс либо распределение по окнам с учётом лимитов. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L153-L184]
  - Контур C — **Агрегатор тарифов транспортных компаний**: единый калькулятор по подключённым ТК, автовыбор минимального тарифа с учётом рейтинга надёжности из контура D, история запросов с привязкой к заказу в 1С. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L186-L212]
  - Контур D — **Платформа взаимодействия с перевозчиками**: модули тендеров на рейсы, расчёт рейтинга подрядчика (доля опозданий и срывов, качество ЭДО, история штрафов), смарт-контракты, встроенное ЭДО (внутреннее или ДИАДОК), штрафной модуль с автоматическим выявлением нарушений, формированием реестра, генерацией претензий и счетов, отслеживанием оплат. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L214-L257]
  - Контур E — **Интеллектуальная сигнальная система предотвращения перезатарки**: прогноз остатка по формуле «текущий остаток + плановый налив − прогноз отгрузок», пороговые предупреждения 90% / 95% ёмкости, рекомендация плановикам. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L269-L294]
- **Внешние интеграции**: 1С УПП (HTTP-сервисы, без файлового обмена и без прямого SQL); WMS (через адаптер); BI-система (накопительный слой и сигналы Контура E); ELMA (webhook для согласования штрафных реестров); ДИАДОК / ЭДО (исходящие претензии и счета, входящие подтверждения); публичные API транспортных компаний (тарифы). При переходе на 1С:ERP меняется только интеграционный слой. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L259-L308]
- **Стек технологий**: «кастомизированная веб-платформа» с REST/HTTP-интеграцией к 1С (явное требование: никакого файлового обмена и прямых SQL-запросов к БД 1С), GUID 1С — ключи связи во всех модулях, stateless-слоты, нейтральный BI-слой, маппинг-таблица полей 1С УПП → 1С:ERP. Точный фреймворк/язык бэкенда и фронтенда в исходниках не задокументированы. ML-составляющая упомянута только для Контура E (сигналы перезатарки) — конкретный алгоритм не задокументирован. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L93-L110,L274-L294]
- **Потоки данных (основной сценарий, бронирование + штраф)**:
  1. Заказы из 1С УПП поступают в платформу через HTTP-сервис; коэффициент сложности (К1–К4) подтягивается из реквизита заказа или справочника «Виды загрузки». [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L140-L151]
  2. Менеджер бронирует окно или подтверждает мастер-заявку (контур B); статус и временное окно записываются обратно в 1С. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L178-L184]
  3. Yard Management фиксирует плановое и фактическое время прибытия ТС; ежедневно по расписанию формируется реестр опозданий с расчётом штрафа по смарт-контракту. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L237-L252]
  4. Реестр уходит на согласование в ELMA; после акцепта ИИ-модуль генерирует претензию по шаблону, автоматически формируются счета, документы уходят через ДИАДОК. Статус оплаты возвращается в рейтинг перевозчика. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L244-L252]

### Ключевые архитектурные решения и трейдоффы

- **«Обёртка» над 1С УПП с готовностью к 1С:ERP вместо кастомизации 1С**. Зафиксирован принцип: меняется только интеграционный слой, бизнес-логика и данные платформы не страдают при апгрейде учётной системы. Альтернатива — дописывать функционал прямо в 1С — отвергнута из-за привязки к версии и зависимости от обновлений конфигурации. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L95-L110]
- **API-first, REST/HTTP-сервисы 1С, без файлового обмена и без прямого SQL**. Это исключает ситуации «последний сохранивший перезаписал чужое», характерные для Excel-режима. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L100-L106]
- **Смарт-контракты с предварительным due diligence перевозчиков**. Условия штрафов фиксируются при регистрации ТК, отдельного согласования по каждому случаю не требуется. Трейдофф — необходимость юридической валидации условий до запуска и ручной override для спорных случаев. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L225-L257,L329-L331]
- **ML-сигнал (контур E) v1 — только дашборд без автодействий**. Сознательный выбор итеративной калибровки с плановиками, чтобы избежать ложных тревог. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L333]
- **Параллельная работа с Excel 2–4 недели на пилоте Yard Management** — мера снижения риска сопротивления пользователей. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L328]

### ИИ / автоматизация в составе платформы

- **ИИ-генерация претензий** в штрафном модуле: после согласования реестра ИИ-модуль подставляет данные в шаблон претензии. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L247]
- **ML-сигнальная система перезатарки** (Контур E): прогноз остатков по горизонту 7–14 дней с пороговыми правилами 90%/95% ёмкости. Конкретный класс модели и обучающий датасет в исходниках не описаны. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L275-L294]
- **Авторейтинг подрядчиков** на основе статистики опозданий и срывов — алгоритмический, без явного указания ML. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L224]

### Информационная безопасность

В тексте описания платформы есть базовые элементы: разграничение ролей в Yard Management (менеджер ОРК, транспортный логист, экспорт, контрактники, начальник склада — каждый видит и редактирует только своё), оптимистичная блокировка для параллельного доступа, история всех бронирований как аудит-трейл. Юридическая валидация смарт-контрактов до запуска отнесена в меры снижения рисков. [источник: 02_ПРОЕКТЫ/Складская_логистика/Описание_платформа_логистка.md:L120-L136,L325-L331]

## Кейс B. Аудит промышленного холдинга и портфель ROI-гипотез (анонимно)

### Один абзац (хук)

90-дневный (фактически — 7-недельный) аудит готовности крупного промышленного холдинга к системному внедрению ИИ: 27 интервью с двумя десятками подразделений, паспорт данных по 16 направлениям, портфель из десятков инициатив с приоритизацией Q1–Q4 (важно × реализуемо), дорожная карта на три горизонта и финансовая рамка-«воронка», в которой каждый следующий рубль разблокируется итогом предыдущего этапа. На выходе — короткий список немедленно стартующих пилотов и инвестиционный портфель, выдержавший защиту перед топ-менеджментом. [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Отчет_аудита_готовности_к_ИИ/02_Контекст_методология_ограничения.md:L14-L24,L29-L56,L108-L120]

### Контекст и задача аудита

Заказчик — крупный промышленный холдинг с собственным производством, R&D, коммерческим блоком, продажами через маркетплейсы и распределённой сетью складов. Базовая ситуация: разрозненные системы (внутренняя ERP, BI, корпоративный workflow, CRM, маркетплейсы, Excel-практики), отсутствие единой архитектуры данных, ограничивающая политика ИБ, ручные процессы во всех функциональных блоках, отсутствие функции «системного перевода» бизнес-болей в техзадания. ### Сформированные ROI-гипотезы (обобщённо)

Ниже — обезличенный фрагмент портфеля. Имена систем, конкретные суммы и доли узнаваемых поставщиков заменены на функциональные описания и порядки. Для каждой гипотезы приведены допущения расчёта, ожидаемый порядок эффекта и срок окупаемости в диапазоне.

1. **Стандартизация заявок на вакансии («HR-фабрика»)**.
   - Боль: разнородные заявки от десятков нанимающих менеджеров, повторная переработка рекрутерами, разный корпоративный стиль.
   - Решение: ИИ-инструмент-«фабрика» для генерации структурированной заявки и профиля вакансии в едином стиле, запускается на внешних API.
   - Допущения: десятки активных рекрутеров; сейчас на одну заявку уходит часы переработок; ИИ-генерация заменяет 60–80% ручной работы.
   - Эффект: высвобождение значительной доли времени HR-команды (порядок — десятки человеко-дней в год).
   - Срок окупаемости: 1–3 месяца.
   - Риск внедрения: низкий (нет коммерческой тайны; согласован на внешних API).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/План_90_дней/Short-лист_проектов.md:L33-L37,L144-L153] [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Краткое_резюме_аудита_для_ГД.md:L58-L59]

2. **ИИ-аналитик постановки задач на ИТ-разработку**.
   - Боль: руководство ИТ-блока оценивает, что ~60% «тормозов» в работе с заявками — низкое качество постановки задач от бизнеса.
   - Решение: чат-бот для формирования корректных ТЗ через наводящие вопросы; снижение нагрузки на системных аналитиков.
   - Допущения: текущий поток заявок исчисляется сотнями в месяц; типизация повторяющихся форматов покрывает большую часть случаев.
   - Эффект: сокращение цикла «заявка → ТЗ» в 2–3 раза, снижение доли переработок.
   - Срок окупаемости: 3–6 месяцев.
   - Риск: низкий-средний (требует приёмки от внутреннего ИТ-блока).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Докладная_записка_итоги_аудита_27.04.2026.md:L49-L54,L175] [источник: 01_АУДИТ_И_СТРАТЕГИЯ/План_90_дней/Short-лист_проектов.md:L43]

3. **Интеграция учётной системы с маркетплейсами**.
   - Боль: рассинхронизация между внутренней учётной системой и витринами маркетплейсов, фиксируемые прошлогодние потери порядка десятков млн ₽.
   - Решение: автоматизация (не ИИ) — двусторонняя синхронизация остатков и заказов через API.
   - Допущения: API маркетплейсов стабильны; есть владелец данных со стороны e-com и финансов.
   - Эффект: предотвращение повторения убытков того же порядка; ускорение реакции на ценовые изменения.
   - Срок окупаемости: 3–6 месяцев.
   - Риск: средний (закрытие части API крупных маркетплейсов требует обходных способов сбора данных).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/План_90_дней/Short-лист_проектов.md:L123] [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Докладная_записка_итоги_аудита_27.04.2026.md:L158]

4. **Транскрибация и саммаризация совещаний с декомпозицией задач**.
   - Боль: общехолдинговая. Ручное протоколирование, потеря договорённостей, нет автоматического перевода решений в задачи и календари участников.
   - Решение: локальный сервис распознавания речи + LLM-постобработка (протокол + список задач). Готовый прототип уже работает на стороне команды автора.
   - Допущения: на момент пилота уже есть GPU-сервер в защищённом контуре; согласован классификатор данных.
   - Эффект: снижение трудозатрат секретарей и менеджеров в разы; сокращение «потерянных» поручений.
   - Срок окупаемости: 6–9 месяцев.
   - Риск: средний (зависит от сроков ввода серверной инфраструктуры).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Краткое_резюме_аудита_для_ГД.md:L54-L55] [источник: 01_АУДИТ_И_СТРАТЕГИЯ/План_90_дней/Short-лист_проектов.md:L61-L65]

5. **Псевдонимизирующий шлюз («анонимайзер») как фундамент работы с внешними LLM**.
   - Боль: ИБ-политика запрещает любую передачу данных во внешние сервисы; коллектив теряет производительность, обходя ограничения «телефоном».
   - Решение: обратимая псевдонимизация ПД, коммерческой тайны, брендов и внутренних идентификаторов перед отправкой в LLM.
   - Допущения: согласована политика классификации данных; есть процесс ревью словарей сущностей.
   - Эффект: расширение круга задач, где можно безопасно применять внешние ИИ-сервисы; снижение риска утечки коммерческой тайны.
   - Срок окупаемости: оценивается не прямой экономией, а разблокировкой портфеля внешних API-пилотов на сумму несколько млн ₽.
   - Риск: средний (зависит от качества детекции сущностей и приёмки ИБ).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/Отчёты_по_аудиту/Краткое_резюме_аудита_для_ГД.md:L29] [источник: 09_ИНФОРМАЦИОННАЯ_БЕЗОПАСНОСТЬ/Guardrails.md:L40-L76]

6. **RAG-навигатор по корпоративным регламентам, СМК и инструкциям**.
   - Боль: разрозненные регламенты и стандарты, ручной поиск нужной нормы, разные ответы у разных сотрудников.
   - Решение: корпоративный «единый ИИ-консультант» по всем регламентам, СТО и СМК. Развёртывается на локальном сервере.
   - Допущения: документы оцифрованы; есть владелец актуальности.
   - Эффект: сокращение времени поиска и согласований; снижение ошибок интерпретации.
   - Срок окупаемости: 6–12 месяцев.
   - Риск: средний (требует поддержки актуальности; есть риск галлюцинаций — HITL обязателен).
   [источник: 01_АУДИТ_И_СТРАТЕГИЯ/План_90_дней/Short-лист_проектов.md:L71-L73] [источник: 09_ИНФОРМАЦИОННАЯ_БЕЗОПАСНОСТЬ/Guardrails.md:L98-L114]

7. **Динамическое ценообразование (стратегический пилот горизонта 2–3)**.
   - Боль: текущая модель цен — экспертная, реакция на ценовые движения конкурентов медленная.
   - Решение: ML-движок ДЦ на интегрированных данных из учётной системы, BI и витрин дистрибьюторов, с history-of-deals не короче нескольких лет.
   - Допущения: завершена консолидация данных; есть исторические сделки достаточной глубины; есть кросс-функциональная команда (коммерция, аналитика, ИТ).
   - Эффект: рост маржинальности на единицы процентов без потери объёма продаж (отраслевой бенчмарк, не цифра на данных заказчика).

## Глоссарий и сокращения

- **TMS** (Transport Management System) — система управления перевозками.
- **YMS / Yard Management** — управление двором, очередью машин и слотами загрузки-выгрузки.
- **WMS** — складская система адресного хранения и отбора.
- **ERP / 1С УПП / 1С:ERP** — учётно-управленческие системы; УПП — «Управление производственным предприятием»; ERP — следующее поколение конфигурации 1С.
- **BI** — Business Intelligence, аналитический слой и дашборды.
- **ЭДО / ДИАДОК** — электронный документооборот / один из российских операторов.
- **ELMA** — BPM-платформа для согласований.
- **RAG** — Retrieval-Augmented Generation, ответы LLM с подкреплением выдержками из корпоративных документов.
- **HITL** — Human-in-the-Loop, обязательная проверка решений ИИ человеком.
- **DLP** — Data Loss Prevention, контроль утечек.
- **SIEM** — Security Information and Event Management, корреляция событий безопасности.
- **HLD** — High-Level Design, верхнеуровневое архитектурное проектирование.
- **СТО / СМК** — стандарт организации / система менеджмента качества.
- **P/I-матрица** — Priority/Impact, матрица приоритизации; здесь — квадранты Q1–Q4 «важно × реализуемо».
- **МВП / MVP** — минимально жизнеспособный продукт.
- **CAPEX / OPEX** — капитальные / операционные затраты.
