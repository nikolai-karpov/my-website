# Как перенести дизайнерскую версию статьи в Хабр

Инструкция для Николая Карпова. Проверено по официальной справке Хабра 29 октября 2026 года.

**Это инструкция по оформлению, не новая редакция текста.** Пояснения «что сделать» и названия шагов в публикацию не переносить. Копировать только отмеченные фрагменты разметки и авторский текст статьи.

Источник: [статья на сайте](https://nikolai-karpov.github.io/my-website/site-pages/team-ai-enablement/habr-article.html).

Важно: копировать текст из открытой страницы, а не из HTML-файла. На странице уже выставлены нужный порядок разделов и место рефлексии; весь текст и схемы в HTML статические.

## 1. Сначала выбери способ работы

Рекомендую **обычный визуальный редактор Хабра**: в нём удобно загружать изображения, задавать подписи и проверять результат. Фрагменты Markdown ниже можно вставлять в него; после вставки убедись, что они преобразовались в форматирование, а не остались строками со знаками `#` и `**`.

Если предпочитаешь писать разметку вручную, **до начала набора** включи Markdown-режим в настройках редактора. В нём нет меню добавления блоков: используй приведённый ниже Habr Flavored Markdown (HFM) и предпросмотр. Не переключай режим посреди сборки в расчёте на безошибочную конвертацию.

Визуальный режим: новая строка → кнопка `+` слева или `/` → нужный блок. В Markdown-режиме эти действия заменяются разметкой.

Сразу сохрани черновик на Хабре, чтобы у него появился ID. Автосохранение в браузере не заменяет сохранённый черновик для работы с другого устройства.

## 2. Что переносится, а что заменяется

| На дизайнерской странице | На Хабре делай так |
| --- | --- |
| Большой журнальный заголовок | Название в отдельном поле заголовка публикации |
| Заголовки разделов | `## Заголовок` |
| Подразделы канона и памяти | `### Подзаголовок` |
| Боковое оглавление | Обычные ссылки на якоря в начале статьи |
| Цветной фон, шрифты, рамки, сетка | Не переносить; использовать стандартное оформление Хабра |
| HTML/CSS-схемы | Простые таблицы/списки из инструкции либо отдельные PNG |
| Изображение слайда | Загрузить картинку блоком «Изображение» |
| Крупные акцентные абзацы | Блок «Цитата» либо жирное выделение одного предложения |
| Имена файлов, навыков и скриптов | Строчный код: обратные кавычки |
| Метка «Дизайнерская версия», меню сайта, дата сайта, футер | Не переносить |

Не вставляй HTML всей страницы, `<style>`, `<script>`, классы CSS, интерактивные схемы или Mermaid-код в надежде получить тот же вид. Для этого переноса используем подтверждённые возможности редактора: текстовые блоки, HFM и растровые изображения.

## 3. Заголовок, вступление и оглавление

### Поле «Заголовок»

Вставь без `#`:

```text
Как я строил ИИ-обвязку рабочего места аналитика в IT-компании
```

Хабр допускает заголовок до 120 символов; этот заголовок укладывается в лимит. Повторять его внутри текста не нужно.

### Начало текста

Перенеси три вступительных абзаца из «От личной практики к корпоративному внедрению». Не вставляй перед ними ещё раз подзаголовок страницы с той же фразой: на сайте это часть оформления, на Хабре получится повтор. Содержание самих абзацев не меняй.

После вступления вставь оглавление:

```markdown
**Содержание**

- [Боевая проверка: комплект бизнес-требований под дедлайн](#case)
- [С чем я пришёл к этой задаче](#experience)
- [Канон и структура проекта](#canon)
- [Зачем канону понадобился владелец](#owner)
- [Как я использовал взаимное ревью агентов](#review)
- [Где канон ломался](#failures)
- [Как инструкции доходили до пользователей](#adoption)
- [Как я организовал поддержку через агентов](#support)
- [Анализ расхода токенов](#tokens)
- [Как я разделил память пользователей и владельца канона](#memory)
- [Что в итоге стало рабочим местом аналитика](#result)
- [Заменит ли ИИ человека?](#human)
```

Для каждого раздела поставь якорь с соответствующим именем. В визуальном редакторе: `+` → «Якорь» → имя без `#`. В HFM:

```markdown
<anchor>experience</anchor>

## С чем я пришёл к этой задаче
```

Не рассчитывай на автоматические адреса заголовков. Явные якоря позволяют проверить каждую ссылку в оглавлении.

## 4. Карта сборки: куда что вставлять

Иди по строкам сверху вниз. Текст между вставками копируй из открытой страницы статьи. Схемы из следующего раздела — готовые варианты для стандартных блоков Хабра; это не дополнительные редакторские правки.

| Раздел и якорь | Что ты делаешь |
| --- | --- |
| `experience` — «С чем я пришёл к этой задаче» | Переносишь текст обычными абзацами. Не превращаешь весь раздел в цитату или спойлер |
| `canon` — «Канон и структура проекта» | Сохраняешь подзаголовки уровня 3. После абзаца «Для принятого комплекта релиза…» вставляешь схему A. После «Качество результата зависело…» — таблицу B. После «Замечания к результату становились…» — процесс C |
| `owner` — «Зачем канону понадобился владелец» | После абзаца «Принятые исправления входят в обновления…» вставляешь процесс D. «Анализ расхода токенов» — отдельный раздел уровня 2; не добавляешь график или плашку ×2 без исходных данных |
| `review` — «Как я использовал взаимное ревью агентов» | Ставишь сразу после владельца. После «Поэтому важно задавать границы проверки…» вставляешь процесс E |
| `adoption` — «Как инструкции доходили до пользователей» | После абзаца «Для обучения специалистов я подготовил…» загружаешь слайд F, добавляешь подпись и ссылку на навигатор |
| `support` — «Как я организовал поддержку через агентов» | После «Когда меня не было у компьютера…» вставляешь процесс G |
| `memory` — «Как я разделил память пользователей и владельца канона» | После первого абзаца оставляешь «Рефлексия как стандарт» и авторские списки. После абзаца «Таким образом, проектная и межпроектная память…» — таблицу H. После «Ещё один слой я хотел бы добавить…» — блок I с явной отметкой, что это план |
| `result` — «Что в итоге стало рабочим местом аналитика» | Оформляешь абзац «При этом скорость генерации документа…» как цитату; исходный экземпляр этого абзаца не дублируешь |
| `human` — «Заменит ли ИИ человека?» | Последний абзац «Профессиональная обвязка позволяет сохранить решения…» оформляешь как финальную цитату. Новую рекламную концовку не добавляешь |

Для остальных разделов шаблон якоря тот же: `<anchor>canon</anchor>`, затем пустая строка и `## Канон и структура проекта`.

Подразделы канона:

```markdown
### Роль, навык и инструмент
### Оцифровка: сохранить смысл источника
### Анализ источников и подготовка документов
### Сборка DOCX и проверка результата
```

Ставь каждый подзаголовок перед своим текстом, как на странице статьи. Не вставляй заголовки подряд без абзацев.

## 5. Готовая разметка вставок

Ниже — вариант без необходимости делать скриншоты всех схем. Таблицы и списки адаптируются лучше мелкого текста внутри картинки. Если вместо блока используешь его PNG, не вставляй ещё раз ту же таблицу или список.

### A. Черновики и релиз

После абзаца «Для принятого комплекта релиза…». В визуальном редакторе для дерева используй «Код», без подсветки языка; акцент ниже — отдельный обычный абзац.

````markdown
**От рабочего документа к принятому комплекту**

```
02-business-requirements/
└── БТ-ЦР-ДБОФЛ-002-Пополнение-СЦР-Клиента-ФЛ/
    ├── md/       — рабочий текст
    └── docx/     — сборки документа
```

**Все материалы в рабочих каталогах — черновики.**

Проверка и приёмка специалистом → отдельный каталог принятого комплекта релиза.
````

Не рисуй каталог релиза внутри `docx/`: это разные места хранения.

### B. Устройство канона

После «Качество результата зависело от согласованности всей связки…».

```markdown
**У каждого элемента — своя работа**

| Элемент | Что задаёт |
| --- | --- |
| Роль | Ответственность и границы полномочий |
| Навык | Методику выполнения задачи |
| Инструмент | Повторяемую операцию |
| Источники | Основания для содержания |
| Шаблон | Форму документа |

Результат — артефакт, собранный на основе согласованной работы этих элементов.
```

В визуальном редакторе: `+` → «Таблица», две колонки. Не делай пять колонок — на телефоне они будут слишком узкими. Эта таблица показывает роли элементов, а не порядок вызова инструментов.

### C. Сборка и приёмка

```markdown
**Сборка — ещё не приёмка**

1. Подготовить текст и назначенный шаблон.
2. Собрать рабочий DOCX.
3. Проверить содержание и оформление, исправить замечания.
4. Передать документ на приёмку специалисту.
5. Поместить принятый документ в комплект релиза.

Замечания возвращаются в инструкцию, профиль или инструмент. Затем документ собирается повторно.
```

### D. Развитие канона

```markdown
**Улучшение проходит через владельца**

Предложение → проверка владельцем → принятое изменение → обновление рабочих мест.
```

Это одна короткая строка с естественным переносом, не таблица и не блок кода. На мобильном проверь, чтобы она переносилась, а не требовала горизонтального скролла.

### E. Взаимное ревью

```markdown
**Ревью с условием завершения**

1. Исполнитель готовит решение.
2. Другой агент проверяет результат.
3. Конкретные замечания возвращаются исполнителю.
4. Исправления проходят повторную проверку.

**При расхождении мнений решение остаётся за человеком.** Согласие моделей не заменяет проверку на задаче.
```

### F. Изображение вебинара

Готовый файл: [designer-webinar-foundations.png](../../assets/images/designer-webinar-foundations.png).

Для скачивания через браузер: [открыть изображение](https://nikolai-karpov.github.io/my-website/assets/images/designer-webinar-foundations.png).

1. Сохрани PNG на компьютер.
2. В редакторе Хабра поставь курсор после абзаца о проведённом вебинаре.
3. `+` → «Изображение» → загрузи PNG.
4. В настройках изображения добавь подпись: **Из вебинара «ИИ в работе аналитика: подход и рабочий цикл».**
5. Под изображением добавь ссылку на навигатор:

```markdown
[Открыть HTML-навигатор](https://nikolai-karpov.github.io/my-website/webinars/navigator.html)
```

Если работаешь в Markdown-режиме, базовая вставка уже доступного изображения:

```markdown
![Три фундамента работы с ИИ: данные, обратная связь и рефлексия](https://nikolai-karpov.github.io/my-website/assets/images/designer-webinar-foundations.png)

*Из вебинара «ИИ в работе аналитика: подход и рабочий цикл».*
```

Для опубликованной статьи предпочтительна загрузка файла на Хабр: так изображение не зависит от дальнейших изменений сайта. Если используешь полученный URL Habrastorage, вставь его вместо адреса GitHub Pages. Не придумывай адрес Habrastorage заранее.

### G. Поддержка

```markdown
**От обращения — к продолжению работы**

1. Специалист сообщает о проблеме.
2. Коммутатор связывает переписку с агентами владельца.
3. Владелец поручает агенту заняться обращением.
4. Агент разбирает контекст и готовит инструкцию.
5. Специалист получает порядок действий для продолжения работы.

Общая проблема становится основанием для изменения канона.
```

Не заменяй этот процесс надписью «Полностью автономная поддержка»: в статье описано участие владельца.

### H. Области памяти

```markdown
**Разные задачи — разные области памяти**

| Область | Что в ней сохраняется |
| --- | --- |
| Проект специалиста | Требования, договорённости и особенности проекта |
| Владелец канона | Общий опыт агентов для развития стандарта |
```

### I. Планируемый слой

```markdown
**Замысел, пока не реализовано**

Опыт проектов и команд → владелец рефлексии → межпроектные уроки.
```

Обязательна текстовая отметка статуса. На Хабре нельзя рассчитывать, что пунктир рамки или её цвет передаст смысл так же, как на сайте.

## 6. Акценты и строчный код

В итоговом разделе выдели существующий абзац и выбери «Цитата». Разметка этого же абзаца:

```markdown
> При этом скорость генерации документа — лишь часть результата. Важно учитывать время на проверку, исправления и дальнейшее использование. Если аналитик получил текст быстрее, а разработчик потратил больше времени на уточнения, оценивать выигрыш нужно по всей цепочке.
```

Это авторская выноска, не цитирование другого человека. Она заменяет оформление абзаца, а не добавляется второй копией.

В финале таким же способом выдели уже существующий последний абзац. Не добавляй новую формулировку вывода от дизайнера.

Имена файлов и навыков оформляй так:

```markdown
`md/`, `docx/`, `project-layout`, `layout-builder`, `scaffold_layout.py`,
`technical-analysis`, `open-questions.md`, `docx-layout`, `preflight.py`, `build_docx.py`
```

Не превращай обычные термины «канон», «рефлексия» и «рабочее место» в код. Не выделяй жирным целые страницы: достаточно ключевого ограничения в визуальной вставке.

## 7. Если хочешь сохранить именно графический вид схем

В статье девять визуальных вставок, из них восемь схем сделаны средствами HTML/CSS и один слайд — PNG. **Восьми отдельных файлов схем сейчас нет.** Они не появятся на Хабре при копировании текста.

Для каждой схемы вместо соответствующей текстовой вставки A–E, G–I:

1. Открой страницу статьи в светлой теме на широком экране.
2. Сделай снимок только схемы, без меню, оглавления и соседних абзацев. Для качественного результата лучше экспорт отдельного элемента, а не обрезка снимка всего длинного экрана.
3. Сохрани PNG. Рекомендация дизайнера: ширина около 1400–1800 px, непрозрачный светлый фон, читаемые подписи; это не техническое ограничение Хабра.
4. Загрузи его через «Изображение» ровно в место из карты сборки.
5. В подписи используй название схемы. Для планируемой памяти добавь «Замысел, пока не реализовано».
6. Проверь уменьшенный вид на телефоне. Если подписи мелкие — используй вместо картинки таблицу или список из инструкции.

Не вставляй снимок всей статьи как одну картинку. Не делай скриншот текста ради переноса шрифтов сайта.

## 8. Настройки публикации

После проверки текста нажми «Готово к публикации» и настрой второй экран. Это ещё не означает, что нужно сразу публиковать.

- Тип: **Статья**.
- Язык: **Русский**.
- Формат: **Кейс** — рекомендация для этого материала.
- Сложность: **Средний** — рекомендация, поскольку предполагается знакомство с аналитикой и ИИ-инструментами.
- Хабы: выбери подходящие из доступных в редакторе, не более пяти. Не добавляй нерелевантные ради охвата.
- Ключевые слова: до десяти, через запятую, без `#`. Возможный набор: `ИИ-агенты, системный анализ, документация, внедрение ИИ, управление знаниями, рефлексия, автоматизация`.
- Вводная часть для ленты: возьми первые абзацы статьи, уложись в 2000 символов. Отдельный `<cut>` не нужен: в новом редакторе анонс настраивается на втором экране.
- Обложка ленты: необязательна. Хабр рекомендует JPG/GIF/PNG размером 780×440. Отдельная обложка для этой статьи пока не подготовлена; не используй мелкую многотекстовую схему только ради заполнения поля.

Фон, шрифт и компоновка сайта не будут перенесены. На Хабре дизайнерское решение сохраняется через порядок чтения, заголовки, понятные схемы и дозированные акценты.

## 9. Проверка перед публикацией

- [ ] В статье нет инструкции из этого файла, редакторских комментариев, метки «Дизайнерская версия» и сравнения старого с новым.
- [ ] Разделы идут в порядке: устройство → развитие и внедрение → сохранение опыта → итог.
- [ ] Рефлексия находится в разделе памяти, а не продублирована у владельца.
- [ ] Все ссылки оглавления приводят к нужным разделам.
- [ ] Нет заголовков ниже третьего уровня.
- [ ] Нет необработанных `##`, служебных HTML-тегов или подписей-заглушек.
- [ ] Для каждой схемы выбран один вариант: изображение либо текстовая вставка, не оба сразу.
- [ ] Изображения загрузились, мелкий текст читается, таблицы удобны на телефоне.
- [ ] Картинка планируемой памяти не выглядит как описание уже работающей системы.
- [ ] Авторские выноски не продублированы в обычном тексте.
- [ ] Нет локальных путей `../../...` в ссылках опубликованной статьи.
- [ ] Анонс и обложка проверены отдельно от тела статьи.
- [ ] Сохранён черновик с ID.

Дизайнерская версия сохраняет авторские формулировки; это не подтверждение готовности всех фактов и названий к публикации. Не исправляй автоматически названия инструментов и числовые результаты при переносе разметки. Их содержательная проверка — отдельная задача.
