## Шаг 0. Собрать десяток в нормализованном виде

**Вход:** десять случаев, как они есть — из логов, тикетов, стенда, памяти.

**Что нужно на выходе — минимальная карточка** (без неё дальше двигаться нельзя):

```
case_id, observed_operation, entity_type, entity_id,
okogu_code_at_creation, record_status, effective_date,
directory_event (annulled / split / merged / renamed / resubordinated),
directory_event_date, source_node, receiver_node,
receiver_directory_version, symptom, source_refs, missing_fields
```

**Роль LLM:** извлечь поля из сырья (лог, тикет, ошибка) в структуру. **Запрет:** заполнять `missing_fields` правдоподобными значениями. Нет данных — `unknown` + поле в `missing_fields`. **Проверка:** JSON Schema + человек смотрит 2-3 карточки.

**Роль человека:** подтвердить, что карточки отражают реальность.

**Почему это первый шаг:** пока десять случаев живут как «истории в голове», никакая абстракция не появится. Это то самое «перевести боль из данных в текст», без которого LLM бесполезна.

## Шаг 1. Матрица осей — найти дырки, а не «проанализировать всё»

**Вход:** десять карточек из Шага 0.

**Что делаете вы (человек):** задаёте оси. Не «пусть LLM найдёт противоречия», а конкретные оси, по которым, как вы подозреваете, живут коллизии:

| Ось | Значения |
|---|---|
| Тип события справочника | annulled / split / merged / renamed / resubordinated |
| Состояние записи | active / closed / in_flight / historical |
| Источник записи | own_node / foreign_node |
| Соотношение дат | record_before_event / record_on_event / record_after_event |

Это ~5 × 4 × 2 × 3 = **120 ячеек**. Не «всё», а **рисковое подмножество**, которое вы задаёте как архитектор.

**Роль LLM:** для каждой ячейки ответить: «есть ли правило, покрывающее эту комбинацию? если да — цитата; если нет — `NOT_DEFINED`; если два правила противоречат — `CONFLICT` со ссылками».

**Выход:** матрица 120 ячеек со статусами. Из них 10-15 — дырки (`NOT_DEFINED` или `CONFLICT`). Это и есть «десяток случаев» в систематическом виде — не те, что уже случились, а **все возможные**, включая те, что ещё не всплыли.

**Роль человека:** решить, какие дырки — реальные кандидаты (а какие — заведомо недопустимые состояния, которые не нужно покрывать).

**Что это даёт:** вместо «сидеть и ждать, пока миграция покажет ещё один случай» — **систематический перебор**. Проверить 120 ячеек дешевле, чем один откат миграции.

## Шаг 2. Для каждой дырки — таблица вариантов, без выбора

**Вход:** одна дырка из Шага 1 + список вариантов реакции, который вы набросали сами (это человеческий брейншторм, не LLM).

Типовой список вариантов для вашей задачи:

| Вариант | Механизм |
|---|---|
| Tombstone со ссылкой на преемника | Запись помечается исторической, хранит `successor_code` |
| Жёсткий отказ | Новая операция с этим кодом отклоняется |
| Ленивая валидация при чтении | Запись хранится, проверяется в момент использования |
| Карантинная очередь | Запись уходит в очередь ручного разбора |
| Окно двойной валидности | Оба кода (старый и новый) считаются валидными N дней |
| Блокировка миграции до ручного решения | Миграция останавливается, ждёт человека |

**Роль LLM:** заполнить построчно: механизм, что ломает, обратимость, драйверы стоимости (какие измерения нужны), прецедент (MDM / LEI / банковские переходные таблицы). **Запрет:** заполнять стоимость числами. Ячейка стоимости = `MEASURE_ON_STAND: <какой эксперимент>`.

**Выход:** сравнительная таблица с **явными дырами для измерений**. Не «лучший вариант», а «вот что известно, вот что нужно измерить, чтобы выбрать».

**Роль человека:** выбрать. Это акт ответственности, не вычисление.

## Шаг 3. Crosswalk — отдельный артефакт, не разовые решения

**Вход:** диф ОКОГУ между версиями (v11 → v12) + список аннулирований/разделений.

**Что делаете вы:** задаёте формат crosswalk:

```
old_code → { new_codes[], type (split/merged/renamed/annulled),
             effective_from, rationale, verified_by, verified_at }
```

**Роль LLM:** сгенерировать кандидатов crosswalk по дифу + классифицировать каждое изменение. Для каждого — пометка `requires_manual_review: yes/no`.

**Роль человека:** подтвердить каждую строку. **Особенно** `new_codes` для split — LLM не выбирает преемника, только предлагает кандидатов по признакам (унаследованное наименование, совпадение родителя, диапазон кода).

**Почему это отдельный артефакт:** crosswalk — это **одно место**, где живёт знание «что во что превратилось». Без него каждый случай решается заново. С ним — каждая новая коллизия сводится к вопросу «что говорит crosswalk для этого кода?».

## Шаг 4. Проверка полноты — через запросы к БД, а не через мнение LLM

**Вход:** ваша абстракция (2-3 класса с критериями членства) + crosswalk + десять карточек.

**Роль LLM:**
1. Разложить каждую карточку ровно в один класс. Аномалии: «0 классов» или «2 класса» — кандидаты на уточнение абстракции.
2. Сгенерировать контрпримеры: «а существует ли запись, где одновременно X и Y?» — каждый контрпример превращается в read-only SQL-запрос.
3. Сгенерировать синтетические тестовые случаи вокруг каждого класса (с разными таймингами, разными версиями справочника).

**Роль человека:** запустить запросы, посмотреть ответы. **Истина — от БД, не от модели.** Если LLM говорит «такая комбинация возможна», а запрос возвращает 0 строк — комбинация не достижима, контрпример отбрасывается.

**Выход:** карта покрытия: `case → class`, плюс список проб (контрпримеры, подтверждённые данными), плюс список «не достижимо в текущих данных».

**Почему это работает:** каждое утверждение модели проверяется внешним оракулом (БД). Это ровно тот критерий применимости LLM, о котором говорили все разборы.

## Шаг 5. Итог: что у вас на руках через эти шаги

Не «красивая абстракция», а **набор артефактов**, с которыми можно жить:

1. **Десять карточек** — нормализованные случаи с `source_refs`.
2. **Матрица 120 ячеек** — где определено, где дырка, где конфликт.
3. **Таблица вариантов** — по каждой дырке, с явными пробелами для измерений.
4. **Crosswalk v11 → v12** — верифицированный человеком.
5. **Классы 2-3** с критериями членства + карта покрытия + подтверждённые контрпримеры.

Каждый артефакт:
- воспроизводим (можно пересобрать из источника);
- проверяем внешним оракулом (БД, тест, crosswalk);
- имеет владельца (человек, который подписал).

**Что это даёт против «боли»:**
- новые коллизии не «всплывают на миграции» — они **попадают в матрицу** и сразу видно, покрыты ли они классом;
- старые случаи не «разбухают» — они **сворачиваются в классы**, поглощённые уходят в архив;
- архитектурный дрифт ловится по **изменению crosswalk или классов**, а не по «модель стала отвечать по-другому».

---

## Что LLM не делает ни на одном шаге

- не создаёт оси матрицы (это акт дизайна);
- не выбирает вариант реакции (нет оракула стоимости);
- не заполняет `new_codes` для split (только кандидаты);
- не утверждает «полнота достигнута» (только «в корпусе X при ограничениях Z проб не найдено»);
- не переписывает классы (только сигнализирует «0 классов» / «2 класса»);
- не правит crosswalk (только предлагает).
