Зачем мы это делаем

ИИ в производственном процессе

Цели

Встроить ИИ в повседневную работу системных аналитиков: разбирать источники и готовить материалы по общему подходу.

Польза для команды

Навыки, над которыми мы сейчас работаем, по значению сравнимы с приходом компьютеров и интернета. Кто их проигнорировал — выпал из рынка. Кто освоил — ушёл далеко вперёд конкурентов.

Польза для компании

Сегодня опыт аналитика живёт у него в голове и дальше не расходится. Мы настраиваем горизонтальное распространение опыта: то, чего добился один, работает у всех.

Рефлексия в конце дня переводит этот опыт в записи: ошибка → решение → правило. Каждый следующий аналитик и каждая следующая сессия агента стартуют не с нуля, а с накопленного.

На этих записях строится корпоративный ИИ, который знает наш контекст, наши документы и наши грабли — вместо покупных синтетических данных.

Сроки и ожидания

Сегодня — показ. На этой неделе — разворачиваете у себя по навигатору. К следующей встрече — первая задача выполнена, результат и время записаны.

Забирает механическую часть

Решения остаются за вами

аналитические решения и приёмку по-прежнему принимает аналитик

Схемы и скриншоты — тоже источник: в пакете есть модели, которые переводят картинки в машиночитаемый вид.

Уже работает на наших проектах:

  • Регуляторика из PDF — в машиночитаемый вид
  • Сверка РП ВС, XSD и ТЗ-Форматы: расхождения отдельно от вопросов
  • Требования к интерфейсу по макетам Figma и БФТ, журнал расхождений по методам
  • UML-диаграммы в формате PlantUML по готовым требованиям — агент строит сам

Ограничения и риски

  • У модели нет кнопки «я не знаю». Правдоподобно — не значит верно. Нет данных — вопрос, а не заполненный раздел. Каждый факт проверяем по источнику.
  • Модель видит только то, что ей дали сейчас. Что не попало в контекст — того для неё нет.
  • Документы клиентов, персональные данные, банковская тайна, данные промышленного контура — в модель не передаются без отдельного разрешения.
  • Модели под корпоративным VPN: китайские модели из пакета провайдера работают, включая Kimi. GPT и Claude — нет.
  • Git — только под корпоративным VPN: commit, push и pull в корпоративный GitLab без VPN не проходят.

Три фундамента работы с ИИ

1Данные

Что не попало в контекст — того для модели нет. Источники — в проект, версия зафиксирована.

2Обратная связь

Плох результат — правим не результат, а постановку или инструкцию. Запрет — через причину, не через «убери».

3Рефлексия

Вечером reflector переводит день в правила. Следующая сессия стартует с накопленного.

Правила и инструкции строим фундаментально. Модель можно сменить: IDE-агент переключает модель под задачу. Правила остаются.

Своя подписка — можно: к IDE-агенту подключаются GPT и другие провайдеры. Claude — только по API, по подписке нельзя. Доступ и VPN для личной подписки — на вас.

Почему IDE-агент

Модель переключается под задачу, подключается любой провайдер. В Золотом стандарте подобраны температура и настройки, чтобы недорогие Flash-модели следовали инструкциям. Флагманы сильны, но дороже и чаще уходят в выдумки.

Золотой стандарт

Общий набор ролей, навыков, правил и инструментов. Одинаков у всех. Репозиторий agent-canon, папка .agent. Проектов в нём нет.

Его же называем каноном: вы им пользуетесь, правит владелец канона. «Подключить в корень» — папка, которую вы открыли в VS Code, становится копией agent-canon.

Адрес: <git-сервер-заказчика>/<группа>/<подгруппа>/agent-canon

projects/ — ваш репозиторий в GitLab под вашей фамилией: рефлексия и все ваши проекты
Золотой стандарт · .agent — у себя не правим, изменения предлагаем владельцу

Обновления канона приходят сами: роль devops проверяет при старте сессии и подтягивает. Ваши проекты она не трогает. Если изменились правила — скажет начать новую сессию. Вручную — «проверь канон».

Три слоя памяти

Память проекта · projects/<проект>/MEMORY.md — как устроен именно этот проект. Читается по фразе «Работаем с <проект>»
Межпроектная рефлексия · projects/reflection/ — опыт, который пригодится во всех ваших проектах. Пишет reflector в конце дня
Бэклог канона — дефект роли, навыка или инструмента reflector отправляет владельцу канона; исправление приезжает всем

Три слоя, чтобы не раздувать один файл и не грузить сессию тем, что ей не нужно: в проекте агент читает только память проекта.

Как пользоваться: агент ошибся → скажите ему, что не так → когда исправил — «Сделай рефлексию». По слоям он разложит сам; заглядывать в бэклог канона не нужно.

Рефлексия

Не контроль и не поиск чужих ошибок. Рефлексия копит реальный опыт команды: какие ошибки встречались и как их решали.

На этом опыте потом строится корпоративный ИИ, который понимает наш контекст.

Как начать у себя

70–79 минут

Как начать у себя: три этапа

Настроить — один раз, до следующей встречи

  1. VS Code + IDE-агент; ключ доступа к моделям выдаёт администратор, заявка через ответственного
  2. Ключ SSH — агент создаёт, копируете кнопкой из ответа → GitLab: аватар → Preferences → слева Access
  3. Клонировать Золотой стандарт из GitLab — он и есть корень; закрыть и открыть VS Code — появятся роли
  4. Окружение .venv и диаграммы — доустанавливает devops; с вас — Python 3.14
  5. Свой репозиторий в <группа>/<подгруппа> — пустой, без README → projects/; подключает devops отдельно от канона: канон и ваши проекты друг друга не затирают
  6. Токены MCP — в .env
  7. Первый запуск reflector — аудит готовности рефлексии

Работать — каждая задача

  1. Источники — в папку проекта
  2. Проект и артефакт — «Работаем с <артефакт> по проекту <имя>»; агент говорит, что прочитал
  3. Роль под артефакт — по навигатору
  4. Проверка; плох результат — правим инструкцию
  5. Вечером — «Рефлексия за сегодня»

Перед первой задачей — завести проект, один раз на проект: следующий слайд.

Грабли первого подключения: автоперевод браузера в GitLab — выключить; ошибка модели видна в строке состояния над полем ввода, а не в чате; .doc пересохранить в .docx. Превью PlantUML — расширение Markdown Preview Enhanced.

Пошагово со скриншотами — в навигаторе (navigator.html в Золотом стандарте), вкладка «Подключение к GitLab». Стартовая страница — в Confluence заказчика: <Confluence-заказчика> · <ID-страницы>

Время: канон — 15–30 мин, всё — около часа. Нет прав — письмо в поддержку подготовит агент.

Завести проект — один раз на проект

1Папка в projects/ → layout-builder: «Сформируй в этом проекте структуру каталогов по канону» + тип: «это коннектор» / «это банковская система». Каркас — каталоги и паспорт раскладки 99-governance/layout.json
2Исходники — в 00-sources/ до первой задачи: архивы распаковать, .doc → .docx, «(1)» убрать; поменяли состав — repo-keeper проиндексирует
3Содержание паспорта проекта — business-analyst на модели поумнее: «Начни с вопросов, ответы на которые помогут тебе сформировать паспорт проекта»
4Шаблоны — в папку шаблонов проекта 98-templates/
5Роль под артефакт: «Работаем с <проект>. Задача: …» + «Верни выводы о готовности начать выполнять текущую задачу» · смотреть open-questions.md
6devops: «выгрузи» → обновить страницу проекта в GitLab

Почему в таком порядке
